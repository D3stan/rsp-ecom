# i18n

UI locales, how dictionaries reach React, locale selection and the locale stored on orders and used by emails. Does not cover email template content (see `email-newsletter.md`).

## Entry points
- `config/app.php`: `supported_locales` (single source of truth) and `default_locale` (from `APP_LOCALE`).
- `app/Support/Locales.php`: supported/fallback helpers and `translations()` (English underneath any locale).
- `app/Http/Middleware/DetectLanguage.php`: picks the request locale; `ShareTranslations.php` shares dictionary and `locale` to Inertia.
- `routes/web.php`: `/api/translations/{locale}` (lazy dictionary load) and `/change-language` (writes session).
- `resources/js/contexts/TranslationContext.tsx`: `t()`, `changeLocale()`; `hooks/useTranslation.ts` only re-exports it.
- `resources/js/lib/translation-guard.ts`: browser-translator crash guard, installed in `resources/js/app.tsx`.

## Rules
- MUST list a locale in both `config/app.php` `supported_locales` and `lang/<code>.json`, and in `DEFAULT_SUPPORTED_LOCALES` of `TranslationContext.tsx`. Enforced by `tests/Feature/LocalesTest.php` (files vs config, frontend constant).
- MUST add every new key to ALL `lang/*.json` files. Enforced by `LocalesTest.php` (every locale has every English key).
- MUST keep `emails.*` keys identical across locales, non-empty, with identical `:placeholders`. Enforced by `tests/Feature/Mail/Content/EmailTranslationsTest.php`.
- NEVER hardcode a locale list in a component (header select, etc.); read `availableLocales` from `useTranslation()`. Enforced by `LocalesTest.php` (header.tsx check only).
- NEVER read a locale from user input without `Locales::isSupported()`. Enforced by `LocalesTest.php` for `/change-language` and `/api/translations`; other call sites Unenforced.
- NEVER change `<html lang>` from JS. The guard compares it with the server value to detect page translation. Unenforced; `translation-guard.test.ts` only tests that a changed `lang` is detected.
- NEVER use `config('app.locale')` as the fallback; use `Locales::fallback()`. `App::setLocale()` overwrites `app.locale` per request/job. Unenforced (only `fallback()` is tested, in `LocalesTest.php`).
- NEVER hand-translate in email views; use `emails.*` keys. Enforced by `EmailTranslationsTest.php`.

## How it works
1. `DetectLanguage` order: session `locale`, then `?locale=` query, then `Accept-Language`, then `Locales::fallback()`. It writes the result back to the session on every request.
2. `ShareTranslations` shares the full merged dictionary plus `locale` on every Inertia response; `app.tsx` seeds `TranslationProvider` with them.
3. Provider locale: if the visitor consented to preferences (`canStorePreferences()`), `localStorage.locale` then browser language win over the server value; without consent the server choice is used.
4. `changeLocale()` sets state, fetches `/api/translations/<locale>` if not cached, POSTs `/change-language`, then `router.reload()` so server-built props switch language.
5. Orders: `CheckoutController` puts `app()->getLocale()` in Stripe metadata; `OrderCreationService::resolveLocale()` normalizes it (`es-ES` to `es`) and stores `orders.locale`.
6. Customer emails use the order locale; internal/admin alerts (`OrderEmail::isInternal`) use `config('app.locale')` (the shop owner's language; a fresh worker has `APP_LOCALE`). An unsupported order locale falls back to `Locales::fallback()`. See `app/Jobs/SendOrderEmail.php`.

## Traps
- Order locale fallback is `it` (`OrderCreationService::FALLBACK_LOCALE` and the `orders.locale` DB default), NOT `APP_LOCALE`. Other jobs/mailables fall back to `Locales::fallback()` (`APP_LOCALE`). Asserted in `tests/Feature/Orders/OrderCreationServiceTest.php` (missing or unsupported locale gives `it`).
- Dictionaries mix nested groups (`cart.shipping`) and flat dotted keys (`settings.tax.rate.label`); `t()` tries the flat key first.
- Catalogue content (product/category names, descriptions) is single-language in the DB; there are no per-locale product texts. Only UI and emails are translated.
- Tests diff dictionaries with `assertTrue(a === b)` on purpose: `assertSame` on two big files exhausts memory.
- `<html lang>` is set server-side in `resources/views/app.blade.php` from the request locale.

## Operate
- `APP_LOCALE`: default/fallback locale (`.env.example` ships `en`).
- Add a locale: add code to `config/app.php`, create `lang/<code>.json`, update `DEFAULT_SUPPORTED_LOCALES`, then run `LocalesTest.php`.

## Tests
- `tests/Feature/LocalesTest.php`: locale list consistency, key parity with English, English fallback merge, switch/API validation.
- `tests/Feature/Mail/Content/EmailTranslationsTest.php`: `emails.*` parity, placeholders, used-vs-shipped keys.
- `resources/js/contexts/__tests__/TranslationContext.test.tsx`, `resources/js/lib/__tests__/translation-guard.test.ts`: provider behavior and translator guard.
